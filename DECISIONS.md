# DECISIONS.md

A running log of product and design decisions settled in conversation — not a codebase reference (see `CLAUDE.md` for that) and not a roadmap. This repo is a fork of `../culinary-canvas-tools` (the Chrome MV3 extension); all product/design history predating the fork — scoring model, vocabulary, theming, tab structure — lives in that repo's `DECISIONS.md` and still applies here unchanged. This file only covers decisions specific to the web-app port.

---

## Standing invariant — privacy (do not break without a deliberate decision)

**2026-10-28 — Gradebook data lives only in the browser and goes only to Canvas; nothing is persisted server-side, and there is no analytics.**
This is the product's core promise, stated here so a future change cannot erode it quietly. Specifically:
- Roster and scores are never cached locally — they are re-derived live from Canvas on every view (see `ScorePanel`/`AttendancePanel`/`KitchenScorePanel`). The only grading state stored in the browser is the per-lab **flags** (not scores) in `storage/labGrading.js`, keyed by Canvas student id with no names. *Since 2026-11-01* that state, the teacher's draft comments, and the setup are also synced to the teacher's own **Canvas custom data**. That copy lives inside Canvas, the district-approved system, and nowhere else (see the 2026-11-01 entry).
- ~~The Canvas token is AES-GCM encrypted under a per-browser key.~~ *Superseded 2026-10-30:* there is no token. The app runs inside the Canvas origin on the teacher's own session.
- ~~The Vercel proxy is a dumb pass-through.~~ *Superseded 2026-10-30:* **no server hop at all.** Requests go from the browser straight to Canvas, same-origin; Vercel serves only static code. `src/api/canvasInPage.test.js` fails if a serverless `api/` directory, a Vercel rewrite, a hard-coded URL, or a bearer token creeps back into production code.
- No analytics, telemetry, third-party scripts, or CDN-hosted assets ship in the app.
Changing any of these (a real backend, cross-device sync, server-side logging) changes the data-handling model and must be a deliberate, documented decision — not a side effect.

**2026-10-28 — iPad: the token is re-entered per device, not transferred.**
Grading happens from an iPad because the laptop is tethered to the podium. The Vercel site makes that possible (the old extension could not), but the per-browser encryption key never leaves its device, so there is no secure transfer path and none is built. The teacher runs onboarding on the iPad once and pastes a Canvas token there. An encrypted export/import was considered and declined as more surface and risk than re-entry is worth.

**2026-10-29 — Reversed the above: added a QR device-link transfer, because grading moved to multiple devices (phone + iPad). Still no server.**
The teacher wanted to sign in on several devices without re-entering the token each time. A real backend (accounts) was explored and set aside: a Canvas developer key for OAuth is not available to a personal tool, and a plain backend would put the token server-side — against the privacy invariant above. A zero-knowledge account was the secure alternative, but the teacher chose the lighter **device-link**: `storage/deviceLink.js` packs the Canvas login (and the `setup` blob if it fits a scannable QR, else login-only) into a QR, encrypted with a passphrase via PBKDF2 → AES-GCM. The passphrase is never shown, transmitted, or stored, so a photo of the QR is useless without it; nothing touches a server, so the privacy invariant holds. The source device shows the QR (`DeviceLinkExport`, in Settings); a fresh device scans it (`DeviceLinkScanner`, on onboarding) and re-encrypts the token under its own per-browser key. Security rests on the passphrase strength — the UI asks for a real passphrase, not a PIN. Dependencies added: `qrcode` (generate) and `jsqr` (decode), both bundled (no CDN), to keep CSP `script-src 'self'` intact.

## The port itself

**2026-10-27 — Forked as a static web-app port; confirmed the extension had no Canvas-DOM or cookie coupling to begin with.**
Audited the extension's entire `chrome.*` surface before committing to the port: no `content_scripts` in `manifest.json`, no `document.cookie`/`chrome.scripting`/`chrome.tabs.query`/`postMessage` anywhere in `src/`. Every Canvas call already went through `fetch` with `Authorization: Bearer <token>` in `api/request.js` — never `credentials: 'include'`. The entire `chrome.*` surface turned out to be shell plumbing only: `chrome.storage.local/sync` (key-value persistence) and `chrome.runtime.getURL`/`sendMessage` (full-page navigation between tool pages, routed through a two-line background service worker). That meant the port was mechanical — swap the storage backend, swap the navigation helper, drop the manifest/service-worker/popup — rather than a rewrite of any business logic. `scoring.js` and the whole `api/*.js` layer ported with zero changes.

**2026-10-27 — ~~Open risk~~ Resolved: Canvas's CORS headers for this page's origin haven't been verified against a live request.**
*Resolved: Instructure-hosted Canvas sends no CORS headers, so the pass-through proxy (`api/canvas.js`) was built and is live on Vercel. Kept below for history.*
The extension's `host_permissions` entry let it bypass CORS entirely — a browser-level exemption tied to the extension's identity, not something Canvas does differently for extensions vs. web pages. A plain web page's cross-origin `fetch` calls are enforced by the browser against whatever `Access-Control-Allow-Origin`/`-Headers`/`-Methods` Canvas's response actually sends back, and that hasn't been tested from a real deployed origin yet. If it turns out Granite's instance doesn't allow this page's origin, the plan is a dumb pass-through proxy (forward only, no logging, no persistence) rather than any other redesign — see CLAUDE.md's "Why this fork exists" section. Don't build that proxy before confirming it's actually needed.

**2026-10-27 — Collapsed the two-tier storage model (chrome.storage.sync + local read-through cache) to a single localStorage tier; cross-device sync is a known, accepted feature loss for now.** *(Sync restored 2026-11-01 through Canvas custom data — see that entry.)*
There's no web equivalent of `chrome.storage.sync`. `storage/kv.js`'s `kvGet`/`kvSet`/`kvClear` wrap `localStorage` directly, and every store (`account`, `setup`, `preferences`, `security`, `auditLog`) was rewritten to call through it — same exported function names and signatures as the extension, so nothing above the storage layer had to change. Consequence, accepted for now: settings/course config no longer follow the teacher across browsers or devices; each browser's `localStorage` is independent. Revisit only alongside a real backend decision (accounts, a sync endpoint) — not worth solving halfway.

**2026-10-27 — Dropped the browser-action popup; the home page (`shell/index.jsx`) is now the only launcher.**
The popup existed because an extension's toolbar icon needs *something* to show. A website has no toolbar icon — visiting `/` (a tiny redirect page) to the home dashboard already does what the popup did (quick links to every tool), so `src/popup/` was deleted rather than ported. `src/background/service-worker.js` was deleted for the same reason: its only two jobs (open onboarding on install, open a tool page on an `OPEN_PAGE` message) don't exist as concepts outside an extension — `SetupGuard`'s existing redirect-if-incomplete check covers the first, and direct `window.location.href` navigation covers the second.

**2026-10-28 — A scoped Professionalism create reads section day-type tags fresh from storage, not from the `courseSetup` state snapshot.**
Symptom: creating a Professionalism assignment "for all B-day sections" right after tagging those sections reached only one section; a second attempt worked. Cause was a stale-state race, not a logic error. Tagging a section writes `localStorage` synchronously (`saveSectionDayType`), but the panel's `courseSetup` state only updates once its `setupVersion`-triggered network refetch (getSections/getAssignments/getModules/getLabs/getCourseSetup, all through the proxy) resolves. A Create fired inside that window filtered `sectionsInScope` against the previous tag set. Fix: `handleCreate` now re-reads `getCourseSetup(courseId)` (a direct `localStorage` read, no network) at the top and uses that `freshSetup` for the scope filter, the professionalism-group check, and the journal offsets. Chosen over disabling the Create button during refetch — reading the source of truth at point-of-use removes the race class rather than hiding its window. The same fix closes the lab-date half of the race: the override loop now derives each section's date as `sectionDueDates[sec.id]` first, then falls back to the day-type quick-set field (`aDate`/`bDate`) keyed on `freshSetup`'s tag, so a just-tagged section gets both its visibility override and its due date on the first create. The resolved dates (not the raw `sectionDueDates` state) are what `saveLab` persists, so the stored record matches the overrides written.

**2026-10-27 — Flagged, not yet acted on: localStorage is more exposed to XSS than chrome.storage was to other extensions.**
An extension's storage is isolated from arbitrary page scripts by the browser; a web origin's `localStorage` is readable by any script that runs on that origin, including a compromised dependency. The AES-GCM-encrypted token and PIN gate are still the right controls, but they're now protecting against a larger threat model (XSS via a supply-chain-compromised npm package, not just "another extension on this browser"). Action item before any real deployment: strict CSP (`script-src 'self'`, no inline/eval), no third-party scripts or CDN-hosted assets, pinned dependency versions. Not done yet — this repo doesn't have a CSP configured as of this entry.

**2026-10-29 — Acted on the above: strict Content-Security-Policy and hardening headers, set in `vercel.json`.**
`script-src 'self'` and `style-src 'self'` with no `'unsafe-inline'`/`'unsafe-eval'`; `connect-src 'self'` is the important line — even if a compromised dependency ran on the page, the browser refuses to send anything (the token included) to any origin but this one, and the proxy only forwards to the allow-listed Canvas host (`ALLOWED_CANVAS_HOSTS`). So a stolen-token-exfiltration path needs both a CSP bypass and a proxy bypass. `img-src` adds `data:` for the device-link QR; `frame-ancestors 'none'` blocks clickjacking; `Referrer-Policy: no-referrer`; `Permissions-Policy` allows only the camera (QR scanner), only for this origin. The root `index.html`'s inline redirect moved to `public/root-redirect.js` so no inline script is needed. Verified against a local serve of `dist/` with these exact headers: every page, fonts, service worker, and QR data-URL image load cleanly, while a test `fetch`/image beacon to an outside host and an injected inline `<script>` are all blocked. The CSP only exists on Vercel — `npm run dev` doesn't send it (Vite's dev server needs inline scripts for hot reload), so a new external resource can work in dev and break in production; it would need adding to the policy deliberately. Canvas tokens are capped at 90 days by the district, which bounds how long a stolen one would be useful.

**2026-10-29 — The Vercel proxy is likely out of FERPA / Utah / Granite compliance; replacing it by running the app inside Canvas (steps 1–3 and 5 built 2026-10-30 — see the entry after the plan).**
*Why.* The proxy logs and stores nothing, but Vercel itself receives the token and students' names, grades, and comments in transit, keeps its own request logs (paths with course/assignment/student ids, client IP; 1 hour on Hobby) as Vercel's own data, and has no agreement with the district. Research against primary sources (34 CFR 99.3/99.31; ED's 2014 "Protecting Student Privacy While Using Online Educational Services"; Utah Code 53E-9-308/-310; R277-487; Granite's Data Governance Plan, which requires Data Security Officer approval and a data-sharing agreement for any third party handling student data) found no exception for teacher-built tools or pass-through-only processing. Vercel's Hobby terms also exclude work use. **Until this ships, don't use the Vercel version with real student data; the Chrome extension (no middleman) is fine meanwhile.**
*Rejected.* Encrypting data through the proxy (impossible — the proxy terminates Canvas's TLS; a TLS-in-the-browser tunnel would work but is experimental crypto to own). Minimizing fields (doesn't help: whoever relays the token can read every record). Any relay on a personal account (same problem). **Google Apps Script** under the district account was built and is covered by Workspace for Education terms, but Apps Script is blocked on district accounts — parked on branch `apps-script-relay` in case the district grants an exception. Native iPad app (needs a Mac and $99/yr; sideloaded builds expire within a year once unpaid).
*Chosen: run the app inside the Canvas origin, launched by a bookmarklet.* Code running on a `graniteschools.instructure.com` page calls the Canvas API same-origin with the teacher's session cookie — no CORS, no token, no relay; student data travels only between the browser and Canvas, and Vercel only serves code. Verified 2026-10-29: Granite's Canvas sends no enforcing CSP (an outside script loaded fine), and a proof-of-concept bookmarklet in iPad Safari read `/api/v1/users/self`, then PUT and DELETEd `/api/v1/users/self/custom_data/poc?ns=org.labtools.poc` with `X-CSRF-Token` taken from the `_csrf_token` cookie — all OK. Session-authenticated JSON can be prefixed `while(1);`; strip it before parsing. iPad note: the Canvas app hijacks tapped Canvas links; typing the URL or using a Safari bookmark keeps it in Safari.
*Plan (teacher chose: open in a new tab; include sync).*
1. **Launcher.** The bookmarklet must call `window.open('')` synchronously (an async step first loses the tap gesture and Safari blocks the popup). The new `about:blank` tab inherits Canvas's origin; the bookmarklet injects `https://<vercel-host>/launch.js?<timestamp>` into it, which writes the app shell (`<link>` + `<script type="module">` pointing at Vercel assets). Module scripts load in CORS mode, so `vercel.json` must send `Access-Control-Allow-Origin: https://graniteschools.instructure.com` on `/assets/*` (and `launch.js`). The tab can't navigate to other pages without leaving Canvas's origin, so the multi-page build becomes **one page with in-app (hash) routing** — a reversal of "each tool is its own page" in CLAUDE.md. Reloading the tab blanks it; relaunch from Canvas (nothing is lost). **Preferred launcher on the iPad (teacher asked for auto-launch):** the free, open-source **Userscripts** Safari extension runs a script on a dedicated Canvas URL (e.g. `https://graniteschools.instructure.com/labtools`, a Canvas 404 page but same-origin and logged in) that replaces the page with the app in that same tab — so a home-screen icon or Safari bookmark to that URL opens the app in one tap, and a reload re-runs the script instead of blanking the tab. Tampermonkey does the same on the laptop if extensions are allowed. Build `launch.js` to support both entry points (take over the current document, or populate a bookmarklet-opened tab). Verify first: does a home-screen web clip to that URL open in full Safari (where extensions run), and is Canvas's 404 page a clean document to take over? Shortcuts was considered and rejected — "Run JavaScript on Web Page" only runs from the share sheet on an already-open page, and can't open a tab without a tap.
2. **Request layer.** `src/api/request.js` fetches `/api/v1/...` same-origin with `credentials: 'same-origin'`, sends `X-CSRF-Token` on non-GET, strips `while(1);`. Same-origin means `Link` and `X-Rate-Limit-Remaining` headers stay readable. `verifyToken` becomes "who am I" (`/users/self`). Remove the token, `storage/encryption.js`, the device link + QR, and onboarding's token step; `SetupGuard` gates on course setup only.
3. **Storage — careful.** In the new tab `localStorage` *is Canvas's own* `localStorage`. Prefix every key (e.g. `labtools:`) and make `kvClear` remove only prefixed keys — the current `localStorage.clear()` would wipe Canvas's data.
4. **Sync.** Back the stores with Canvas custom data (`/api/v1/users/self/custom_data/<key>?ns=org.labtools`), `localStorage` as a cache. Last-write-wins per key for settings; merge `labGrading` flags per student so two devices grading at once don't clobber each other. Student-linked flags then live inside Canvas — the district-approved system.
5. **Retire the proxy.** Delete `api/`, drop the rewrite, re-scope the CSP to the now code-only Vercel site, replace the home page with bookmarklet install instructions, update CLAUDE.md and the privacy invariant (the proxy bullet becomes "no server hop at all").
6. ~~**Tell the district** (Data Security Officer / Director of Ed Tech): a short "here's my tool and how it handles data" note — no third party now touches student data, so it should be an easy yes.~~ *Cancelled 2026-11-01 by the teacher.*
*Risks accepted.* The app's code runs with the teacher's full Canvas session, so a compromised GitHub or Vercel account could ship hostile code — keep 2FA on both (Subresource Integrity was considered, but it would mean re-editing the bookmark on every release). Works in Safari/Chrome, not the Canvas app.

**2026-10-30 — Built plan steps 1–3 and 5 (launcher, same-origin requests, prefixed storage, proxy retired). Sync (step 4) and the district note (step 6) remain.**
- *about:blank is cookie-averse in Safari.* The bookmarklet tab shares Canvas's origin, but `document.cookie` reads empty in an about: document per spec, and `location.origin` is `"null"`. So the bookmarklet reads `_csrf_token` in the Canvas tab and passes it and the origin on `window.__LABTOOLS__` (`api/canvasContext.js`). Any masked copy of the CSRF token validates for the whole session, so one captured at launch lasts until the session ends. Chrome happened to expose the cookie to the about:blank document anyway; the fallback is what Safari will use.
- *One build serves both launchers.* `launch.js` wipes whatever document it's in (an empty about:blank tab, or Canvas's 404 page at `/labtools`) and writes the app shell, so the bookmarklet and the userscript share one code path. It's generated at build time with the hashed bundle names and the theme-init script inlined.
- *Local dev keeps a token proxy, local-only.* `npm run dev` proxies `/api/v1` to Canvas with `CANVAS_DEV_TOKEN` from `.env.local`. It runs on the teacher's own machine, so no third party sees anything. It was chosen over loading the dev server into Canvas (HMR over CORS is brittle).
- *Service worker retired with `selfDestroying`.* The old Vercel-hosted app was a PWA. Devices that still have its worker get one that unregisters itself and clears its caches on their next visit.
- *Data doesn't migrate.* Settings, course setup, and drafts saved in the old Vercel origin's `localStorage` don't carry over to the Canvas origin (different origin). Course setup is re-entered once.
- *Verified against a mock Canvas* (session cookie, `while(1);`, CSRF-checked writes; the app served cross-origin with the `/assets` CORS header): launch into an about:blank document, onboarding, `/users/self`, a CSRF write, two-page pagination, all keys prefixed, userscript takeover of a 404 page, and hash routing that survives reload. **Not yet verified on real Canvas or iPad Safari** — specifically: Safari's pop-up handling of the bookmarklet, whether Userscripts injects on Canvas's 404 page, and whether a home-screen web clip opens in full Safari, where extensions run.

**2026-11-01 — Built plan step 4: cross-device sync through Canvas custom data. Step 6 (the district note) cancelled.**
- *What syncs, and where.* `preferences`, `setup` (courses, labs, terms, lab flags), and grading state go to `/api/v1/users/self/custom_data/<doc>?ns=org.labtools` on the teacher's own Canvas user. Grading state includes flags, presence, and draft comments by student id. The PIN and lockout state (`security`), the activity log, and onboarding status (`meta`) stay on each device, like a phone passcode. Each device runs onboarding once and sets its own PIN. Student-linked data now lives in Canvas as well as the browser, and still nowhere else, so the privacy invariant holds.
- *localStorage stays the working copy.* Every store reads and writes it as before. `kvSet` notifies `storage/sync.js`, which pushes the changed document about 1.5 s later, or right away when the tab is hidden, since the iPad may suspend it. Changes waiting to go up are tracked in `sync:dirty`, so they survive a reload and go up on the next launch. If Canvas is unreachable, the app keeps working locally, shows a header icon, and retries every 30 s.
- *One document per lab for grading.* `labGrading` moved from one key to `labGrading/<labId>` (migrated on launch), so a draft autosave re-sends one lab, not the whole year.
- *Documents are stored as JSON strings.* Canvas parses custom data sent as nested request params, which can change numbers, booleans, empty arrays, and nulls. A string round-trips exactly.
- *Conflicts: three-way merge, field by field (`storage/merge.js`).* Sync keeps a base: the last copy both sides agreed on. A push re-reads Canvas and merges, so two devices editing different labs, periods, or students both keep their edits. If both changed the same value, the device pushing last wins. Arrays, such as a student's flag list or the comment library, are replaced whole. Copies that existed before sync have no base, so they are unioned rather than overwritten.
- *Sync never deletes local data because Canvas lacks it.* It re-uploads instead, so a failed or empty read can't wipe a device. The cost: Settings → Reset's "also erase the synced copy in Canvas" only stays erased if the teacher's other devices are reset too. The UI says so.
- *Launch waits for the first pull, up to 5 s.* Pages then load already-merged data. Changes that arrive later, from a late pull or a pull when the tab regains focus, show an "Updated from another device · Refresh" banner rather than remounting under the teacher mid-grading.
- *Reset no longer loses course setup.* "Forgot your PIN? Reset this device" first pushes anything not yet uploaded, wipes the device, then pulls everything back. Only the PIN and the activity log are lost.
- *Verified* with unit tests (two simulated devices against one fake Canvas) and in the browser against a mock Canvas: legacy migration and upload, a fresh device pulling setup, the banner on a remote edit, a preference push, reset with and without erase, and offline fallback. **Not yet verified against real Canvas**, specifically whether `custom_data` accepts these paths and payload sizes. Check that during the iPad test.
- *First iPad run: sync failed with a 400.* The mock answered a missing document with 404. Real Canvas answers 404 only when the namespace has never been written. Once it exists, a missing path is **400 "no data for scope"**, which is from memory of Canvas's source and not yet confirmed. So after the first upload created the namespace, every check for a document not yet uploaded failed. `api/customData.js` now reads both as missing; a 400 with another meaning resurfaces on the upload that follows. Canvas's error message is now included in `ApiError`, so the status shows Canvas's reason. `ns` is sent in the query string too, matching the proof-of-concept request.
  - *Confirmed 2026-11-01 on real Canvas* (laptop Chrome): a missing path, an empty namespace, and a never-used namespace all answer 400 "no data for scope". After the fix, setup and preferences uploaded, and the Settings card showed "Synced".

**2026-11-02 — Testing aids: debug (dry-run) mode, grade safety checks, error codes and a diagnostics log. Built on branch `debug-mode`; merge only after the teacher verifies on real Canvas.**
*Why.* The teacher wants to prove every feature works and never send a broken score or comment to a student by accident, without testing live.
- *Debug mode never writes to Canvas, but reads real data.* Writes are recorded with a plain-English line, the exact comment the student would see, and the full body. Creates return fake `debug-N` ids so multi-step flows run to the end. A coverage checklist shows which kinds of write have been tried. Known limit: nothing is created, so pages that re-read Canvas after a create don't show the new item; the report is the record.
- *Debug mode is a sandbox, and it's off on every relaunch* (teacher's choice). Local data is copied under `labtools-debug:` and sync is paused, so test edits and fake ids can't reach real data, other devices, or custom data. The switch lives in memory only, so it can't be left on by accident; a striped bar shows on every page while it's on.
- *Safety checks block only what can only be a bug*, in live and debug alike: a score that isn't a non-negative number (the commit loop could post `"null"` for a student with no derivable score), a blank comment, `undefined`/`null`/`NaN`/`[object Object]` in a comment, a non-Canvas id, or any live write to a `debug-N` id. A score above 4 on professionalism and duplicate comments only warn. A block throws `CheckError` (`LT-CHECK`), so the commit loop counts that student as failed and carries on.
- *Error codes.* Every failure gets an `LT-` code, the operation, Canvas's own message, and a next step. Fixed along the way: every 403 used to read "Rate limited"; now only a 403 whose body says so does (`LT-403R`), and the rest are permission errors (`LT-403P`). A dropped connection is now `LT-NET` instead of Safari's bare "Load failed".
- *Diagnostics log.* The last 50 failures on this device are kept locally and never synced, including the per-student failures the commit loop used to swallow silently.
- *Copy for Claude strips student data* (teacher's choice): names, student ids, well-formed scores, and comment text are replaced. Broken values are kept, since they're the bug. Pasting into a chat sends the text to Anthropic, which is outside the district's systems.
- *Toasts:* timings unchanged; the teacher confirmed the current behavior is intentional. Pause-on-hover now responds to a real mouse only, so an iPad tap can't freeze a toast.

**2026-11-02 — One source of truth for deductions and the comment bank: the main Settings page (Grading card). Grading policy stays per course.**
- *Deductions are the lab flags*, already one global list. They stay as two kinds, kitchen (Minor/Major, scored together for the whole kitchen) and individual (each drops one student a tier), because they score differently. The teacher confirmed keeping them separate.
- *Removed* the per-course "Deduction reasons" and "Deduction scoring" settings. They only fed the unwired `ScorePanel` (the old deduction model), so editing them did nothing.
- *The comment bank is global* (`setup.commentLibrary`, `getCommentBank`/`saveCommentBank`). Until it's first edited, it reads as every course's old `settings.commentLibrary` merged, in first-seen order without duplicates, so nothing is lost.
- *Kept per course* (teacher's choice): top score, zero journal when absent, send flag summary as a comment, journal due/close offsets, the Focus sync toggles, and the course's own structure (A/B sections, Terms).

**2026-11-02 — Individual flags get Minor/Major too, weighted like kitchen flags.**
The teacher wanted the two kinds consistent, and asked to keep the kitchen model. Read as: a Major counts as two Minors. So an individual Minor drops the student one tier below their kitchen's score, a Major two, never below 1 (`individualPenalty` in `config/labFlags.js`). Every built-in individual flag is Minor. A saved flag with no severity, or a removed one, also counts as Minor — exactly the old one-tier rule — so already-graded labs keep their scores. *Not done:* pooling a student's own flags into their kitchen's threshold count. That reading would have changed committed scores (kitchen 2 + one individual Minor would become 2, not 1).

**2026-11-02 — Lab tab commit rebuilt around a plan: preview, Canvas-excused absences, revert, period checkmarks. Fixes from a code review.**
- *One plan, previewed and then run* (`pages/labs/commitPlan.js`, pure and tested). It reads Canvas fresh — professionalism scores, excused states and comments, the journal's, and existing journal locks — then decides each student's writes. "Commit Period…" shows that plan before anything is sent: scores by value, comments, absences, excused, students back from absent, students skipped as already up to date, and any blocked by a safety check, with a per-student list. The commit then runs the same plan (`commitRun.js`), re-reading Canvas first.
- *Recommits only send what changed.* An absence already zeroed and locked is left alone. Before, every recommit made a duplicate journal lock that Canvas rejects, so each absent student failed every time.
- *Absent → Present now undoes the absence:* the journal zero is cleared (or un-excused) and the lock removed. This only happens for students committed absent last time, so a real journal 0 is never touched.
- *Excused uses Canvas's own excused* on professionalism and the journal (teacher's request), replacing "zero + an 'Excused absence' comment". An old journal lock is removed. Absent and excused students never get the kitchen's flag summary as a comment.
- *Revert* (teacher's request). Each commit stores, per student, what Canvas held before (`lastCommit` in `storage/labGrading.js`). "Revert last commit" restores scores and excused states, deletes the exact comment it posted, removes a lock it created (or recreates one it removed), and turns the reverted grading back into a draft. It covers one step only, the most recent commit of a period, and overwrites any hand edit made in Canvas since.
- *Period checkmarks.* The period picker shows ✓ for a committed period with nothing unsaved, and • for unsaved edits.
- *Other review fixes:*
  - Resuming or reopening a period kept only kitchen, flags, present and excused, so Exceeds and comments were silently dropped (and Exceeds students then posted the soft top). It now keeps every field.
  - A slower load for a period already left could overwrite the screen and autosave into the wrong period. Loads are now cancelled when you switch.
  - A partly failed commit used to clear the draft; it now keeps it and names the students that failed.
  - A pending autosave could land after a commit and resurrect a draft. It's now cancelled.
  - The Exceeded chip showed the soft top but posts a true 4; it now says 4.
  - Unit/Term: the Unassigned group can't be pushed, which had created a stray "Unassigned … (Unit Score)" assignment. Pushed unit scores now feed the Term rollup without a reload.

## Kitchens, deleting, and the Professionalism list (2026-11-02)

**2026-11-02 — Kitchen placements carry over between labs.**
Kitchens used to live only inside each lab's grading state, so every new lab started with the whole period "Unassigned". Now each period has *standing* kitchens (`storage/kitchens.js`, one synced key per course, `kitchens/<courseId>`, Canvas student ids → kitchen number, no names). A new lab, and any student a lab hasn't placed yet, starts from them. Moving a student in any lab updates them, so the latest arrangement wins. A lab's own state still records who was in which kitchen that day, so reopening an old lab shows its real kitchens. A period with no standing kitchens is seeded once from its most recently touched lab. Kitchens are fixed at 8 (the Kitchens count picker is gone): every room has eight.

**2026-11-02 — Professionalism assignments can be deleted, from Canvas or from Lab Tools only.**
Each row in the list has a delete button. The dialog offers **Delete from Canvas too** (the assignment and every score on it; PIN always required, `forcePrompt`) or **Remove from Lab Tools only** (Canvas keeps it). It reads Canvas first and says how many students have scores. Both clear the lab's saved grading. The paired journal is never touched, and its section dates stay. Labs now record an `origin` (`created` / `reused` / `linked`); delete-from-Canvas is the default only for ones Lab Tools created (and for older labs saved before `origin` existed), but it's available for all.

**2026-11-02 — The Professionalism tab leads with the list; create and link open on demand.**
The tracked assignments used to stack above the create form, pushing it further down with every lab. Now the tab is one list, newest lab first, showing type, dates, unit, and journal, with search and a unit filter once there are more than five. The list scrolls inside its card. **New** and **Link existing** open their forms above it. With nothing tracked yet, the create form shows on its own.

**2026-11-02 — Scores changed in Canvas are never overwritten without asking.**
Students make up labs at home, and the teacher types the makeup score straight into the Canvas gradebook. Before this, recommitting a period re-posted the absence 0 over the makeup, re-zeroed the journal, and re-locked it, and Revert put back the pre-commit score. Now each commit stores `posted` per student: what Lab Tools left on the professionalism assignment. The next commit compares Canvas against it (periods committed before `posted` existed fall back to the committed flags). A student whose score differs, whose graded journal (anything but 0) would be zeroed, or whose journal lock was removed, is **held**: listed under "Changed in Canvas" in the preview with an **Overwrite** toggle, off by default. The journal and lock are held along with the score. Revert does the same check against what the commit posted. A score typed into Canvas before Lab Tools ever committed that period counts too. Revert can't check records saved before `after` was kept.

**2026-11-02 — Kitchen and delete fixes from the code review.**
- Kitchens: always 8, but a lab saved with more still shows them, so no student disappears. A kitchen move counts as the period's usual kitchens only in the latest lab (labs dated after today don't count), so fixing an old lab doesn't change next week's start. Seeding never blocks the roster, and runs once per period.
- Delete: "Delete from Canvas" offers to undo the lab's journal absences: clear absent students' journal zeros and remove their locks, leaving any journal with a real score alone. Without this, nothing could undo them once the lab was gone. "Lab Tools only" now needs the PIN (it's audit-logged) and keeps the lab's saved grading. Labs with no recorded origin start on "Lab Tools only". A failed score check says so instead of reading as "no scores".

**2026-11-02 — Unit and Term scores: a plain average of the labs, nothing dropped, no automatic zero.** (Decided; built in the rollup work.)
Makeups (2 per semester, 1 per term, tracked in a separate Canvas assignment) make an absence zero a placeholder, not a final grade. Dropping the lowest lab and "missed half → 0" were built for permanent zeros. The 50% rule double-counts absences that already score 0, and it creates a cliff: one makeup could move a unit from 0% to about 67%. Both levels now average their labs on the 4-point scale, so the Term weights each lab equally, however labs split into units. Excused labs don't count; blank labs are flagged.

**2026-11-02 — Scoring tab: status at a glance, previewed and revertible pushes, Terms set up in Scoring.**
- Rules as decided above: Unit and Term are plain averages of their labs. A Term now averages its labs directly instead of averaging Unit score assignments, so it no longer depends on Units having been pushed first.
- Each Unit and Term shows **Not pushed**, **Up to date**, or **Out of date (N)**: computed live from Canvas, comparing the current average with what the score assignment holds. A makeup or regrade after a push shows up here.
- Per lab, the period chips show which periods have grades. A Unit can't be pushed while a lab has no grades in any period. If a lab is graded in some periods but not others, that's only a warning.
- **Push** works like Commit Period (`rollupPush.js`): a preview, only changed scores sent, a score Lab Tools pushed is cleared once no labs back it, excused is never touched, and a score changed in Canvas since Lab Tools pushed it is held with Overwrite (and Overwrite all). That includes scores that were already there before tracking began. **Revert last push** restores the scores from before, skipping any changed since. What was pushed is kept in `storage/rollups.js` (synced, `rollups/<courseId>`).
- A new Unit score assignment is added to its Module. Its assignment group is unchanged (Canvas's default) pending a decision: putting it in the Professionalism group could double-count labs if that group is weighted.
- Terms moved from Course Settings to the Scoring tab ("Edit Terms"). A Module already in another Term is dimmed, since its labs would count in both.

**2026-11-02 — Unit and Term score assignments go in the Professionalism group.** Decided by the teacher. They're created there, and in their Unit's Module.

**2026-11-02 — Wording and Grade-tab polish.** "Period" everywhere instead of "section". "Exceeded (4)" for both kitchen and student. Present/Absent is one switch: green and "Present", or red and "Absent", never both words at once. Revert sits beside the commit status, away from Commit Period. Lab dates show as a range ("Nov 2–3"). The Journal picker shows likely lab journals, with all assignments behind a checkbox. No tool menu while there's one tool. Course names are shown without Canvas's term suffix unless two share a name. "Standalone" stays on the Grade list: it shows the lab isn't attached to a journal. No "Commit day": the period buttons and the "not committed yet" warning cover the need.

**2026-11-02 — The commit check reports facts; the teacher never declares a period committed.** A period is ✓ when its last commit matches what's on screen. A draft identical to the commit (an edit undone) is not unsaved work, and it's cleared. When the commit preview finds Canvas already holds exactly what the period would send, with nothing to write and nobody held as changed in Canvas, the app records the period as committed itself (the previous commit stays the one Revert undoes). There is deliberately no "mark as committed" button: if anything differs, the period stays unsaved until a real commit.

## Kitchen Rotation (2026-11-04)

**2026-11-04 — Kitchen Rotation comes into the app as a second tool, kept separate from Labs.** Ported from `../kitchen-rotator` (route `rotation`, `src/pages/rotation/`). The standalone keeps working; this one adds sync across devices. Decided by the teacher: as little overlap with the Labs tool as possible for now, with merging the two to be discussed later. It doesn't touch `kitchens/<courseId>`, `labGrading`, or lab attendance. Its absences are daily, cleared at the next rotation or overnight, as in the standalone. It reads the Labs setup only to list the enabled courses when starting a class, and never writes it. Nothing it does writes to the gradebook, so there's no PIN gate or commit flow. Its only Canvas writes are its own synced documents.
- **The roster comes from Canvas.** Seats hold Canvas student ids. Names are read live and shown as "Kelly A." (more of the last name where two would clash). A new class is shuffled into kitchens from its section, about 4 to a kitchen. A student new to the section shows as "Not seated yet" for the teacher to place. A student no longer in the section leaves their seat, unless the section comes back empty, which is treated as a Canvas hiccup. CSV/paste import and the JSON backup are gone; sync covers backup.
- **Each class is linked to a Canvas section.** "Start a class here" lists the sections and suggests the one whose name matches the period ("1A" → A1, "6B" → B2, since B day runs periods 5–8 in the same four slots).
- **Storage.** `rotation`: the whole board, synced. `rotationHistory/<blockId>`: one class's participation records, synced, last 90 rotations each. Records carry their job titles and student ids, and names are resolved when the CSV is exported. A student who has left exports as "Former student".
- **Attendance is keyed by student, not by seat**, which removes the standalone's carry-marks-across-by-name logic. Undo stays one in-memory step.
- **Known limits.** Size checked on real Canvas (2026-11-04): one custom-data document of 60, 120, 250 and 500 KB each saved and read back whole, and one class's 90 records run roughly 60 KB. A limit on the namespace's total size wasn't tested. If two devices rotate the same class before syncing, the last device to push wins the seating and cursors, and the refresh banner is the guard.
